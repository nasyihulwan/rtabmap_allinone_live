### Root cause "robot tidak gerak" — SUDAH KETEMU & DIPERBAIKI (bagian 1 dari 2)
**Custom BT (`navigate_to_pose_w_smoothing.xml`, dibuat sesi kemarin) TERBUKTI BUGGY di robot fisik:**
- Gejala: `planner_server` & `bt_navigator` error terus-menerus: `"Extrapolation Error: Lookup would require extrapolation into the past"` — request TF pakai timestamp BEKU dari saat goal pertama diterima, padahal buffer TF terus maju. Setelah >~10 detik, lookup itu SELALU gagal.
- Akibat: `cmd_vel` TIDAK PERNAH terpublish sama sekali. Goal selalu berakhir `ABORTED` setelah 5x recovery gagal (spin/wait/backup semua timeout).
- **A/B test empiris** (dites langsung, bukan dugaan): ganti ke BT bawaan nav2 (`navigate_to_pose_w_replanning_and_recovery.xml`, tanpa smoothing) → `number_of_recoveries: 0`, path progress normal.
- **FIX SUDAH DITERAPKAN & DI-SYNC ke kmp-orin:** `default_nav_to_pose_bt_xml` override DIHAPUS dari `launch/nav2_husky.launch.py` — bt_navigator sekarang pakai BT bawaan nav2. Custom BT file tetap ada di `config/behavior_trees/navigate_to_pose_w_smoothing.xml` kalau mau didebug lagi nanti, tapi JANGAN diaktifkan lagi sampai bug timestamp-nya ketemu akar masalahnya.
- **Pelajaran:** path-preview test (`ComputePathToPose`+`SmoothPath` manual, tanpa Husky fisik, sesi 2026-07-07) TIDAK PERNAH mengekspos bug ini karena tidak pernah lewat `RateController` retry loop `bt_navigator` yang sebenarnya — manual test cuma panggil action sekali, bukan looping tiap 1 detik seperti BT asli.

### Root cause kedua — SUDAH KETEMU & FIXED: AMCL message-queue overflow
**UPDATE AKHIR SESI: SUDAH SELESAI.** Root cause asli BUKAN queue depth, BUKAN CPU load, BUKAN "node wedged" biasa — **penyebab sebenarnya: clock/timestamp yang tidak konsisten di beberapa node long-running, dipicu oleh percobaan clock-sync manual yang saya lakukan di tengah sesi.**

**Kronologi penemuan:**
1. Gejala awal: AMCL terus-menerus log `"Message Filter dropping message: frame 'velodyne' ... discarding message because the queue is full"` — bertahan lewat 6x restart bersih, full reboot kedua mesin, penurunan CPU load (26→7), semua gagal.
2. Saya coba ukur clock skew antara kmp-orin & PC Husky (metode sandwich: baca waktu kmp-orin sebelum+sesudah baca waktu PC Husky) — ketemu skew konsisten ~300ms (PC Husky lebih cepat). Saya **set ulang clock PC Husky pakai `date -s`** biar sinkron dgn kmp-orin.
3. **INI MENYEBABKAN INSIDEN KEAMANAN:** ~2 detik setelah clock di-set, joystick F710 di PC Husky disconnect-reconnect tiba-tiba (kemungkinan besar krn perubahan clock mendadak bikin kernel/USB subsystem bingung) — dan **robot bergerak maju sedikit sendiri** tanpa ada goal navigasi aktif (Nav2 stack bahkan sedang dimatikan saat itu). Root cause pergerakan: `twist_mux` kasih prioritas tertinggi ke joystick, kemungkinan reconnect glitch kirim sinyal analog yang salah terbaca sesaat.
4. AMCL yang direstart SETELAH clock-sync itu justru **CRASH** dgn `std::overflow_error: Input t_sec is too large or too small for tf2::Duration` — bukti nyata ada state timestamp yg corrupt/tidak konsisten.
5. **FIX FINAL:** restart SEMUA node yang menyentuh TF (bukan cuma AMCL) SETELAH clock sudah settle — `relay_tf`, `relay_tf_static`, ketiga `static_transform_publisher` (tf_base_to_velodyne, tf_base_camera, tf_bridge_base) — supaya semua node itu punya basis waktu yang konsisten dari awal, tidak ada yang "straddle" momen clock jump. Dikombinasikan dgn `save_pose_rate: 0.5 → 0.0` (AMCL jadi gak nulis pose ke disk periodik tiap 2 detik — awalnya diduga jadi penyebab utama krn periode drop ~2.5 detik cocok dgn ini, tapi ternyata BUKAN faktor utama; tetap disimpan sbg optimisasi minor krn tidak ada downside, `/amcl_pose` topic tetap real-time).
6. **HASIL:** `map->odom` TF stabil, AMCL createLaserObject sukses, ZERO drop selama 40+ detik pengamatan setelah fix ini diterapkan.

**⚠️ PELAJARAN KRITIKAL — JANGAN ULANGI:**
- **JANGAN PERNAH ubah system clock (`date -s` atau sejenisnya) di PC Husky (atau mesin manapun yg terhubung ke motor/joystick robot) SAAT robot dalam kondisi live/joystick terhubung.** Ini punya efek samping fisik nyata (robot bisa bergerak sendiri tanpa perintah eksplisit). Kalau HARUS sync clock, pastikan dulu: joystick dicabut/di-disconnect, atau motor di E-stop, SEBELUM ubah clock.
- Kalau ada indikasi clock skew antar mesin di masa depan, PAKAI NTP/chrony (sinkronisasi bertahap otomatis) BUKAN `date -s` manual (yang bikin lompatan waktu instan/discontinuous).
- Setelah clock berubah (sengaja atau tidak) di mesin manapun, **restart SEMUA node long-running yang menyentuh TF/timestamp** sebelum menyimpulkan sesuatu "masih rusak" — node yang sudah lama hidup bisa punya state waktu yang "straddle" lompatan clock dan berperilaku aneh (drop pesan terus-menerus, bahkan crash) sampai di-restart fresh.

**Config final yang dipakai (sudah di-sync ke kmp-orin):**
```yaml
amcl:
  ros__parameters:
    save_pose_rate: 0.0   # dari 0.5 — matikan periodic pose-save ke disk
```

### C) `relay_tf` crash berulang (2x hari ini)

Gejala: `/tf` topic kosong padahal proses masih ada di `ps aux`. **Bukan config bug**, kemungkinan resource/race condition transient. Fix: restart node itu spesifik (bukan seluruh stack).

### D) `pkill -f velodyne` — JANGAN PAKAI LAGI, self-kill bug
`pkill -f <pattern>` di SSH command mencocokkan SUBSTRING PATTERN itu sendiri di command line SSH yang menjalankannya (krn command line SSH-nya sendiri literally mengandung kata "velodyne")! Ini bikin SSH session mati sendiri SEBELUM sempat relaunch velodyne. **Selalu kill via PID eksplisit**, jangan `pkill -f` utk nama proses yang ada di dalam command SSH itu sendiri.

### E) Custom BT smoothing (dari sesi 2026-07-07) — LIHAT BAGIAN 2, DIMATIKAN

### F) Joystick manual override (F710) — sempat rusak, SUDAH FIX
Receiver F710 di PC Husky (`/dev/input/f710`) sempat disconnect terus-menerus akibat insiden clock-change (lihat bagian 2). **Fix: `sudo systemctl restart clearpath-platform.service`** (password: `rslab123`) — dikonfirmasi stabil, data `/a200_1060/joy_teleop/joy` ~19.6Hz konsisten, gak ada disconnect baru selama 30+ menit pengamatan. Kalau mau pakai sbg safety override besok, tetap test dulu tekan tombol & cek `/a200_1060/joy_teleop/joy` publish sebelum benar2 mengandalkannya (history-nya emang flaky, walau sudah stabil pas terakhir dicek).

### G) `bms/state` topic tidak bisa di-echo — root cause: koneksi fisik marginal (bukan software)
`battery_state_estimator`/`battery_state_control` (di PC Husky) — investigasi mendalam ~6 menit polling manual nunjukin pola INTERMITEN stabil ~75-87% success rate (bukan kerja-lalu-total-mati, tapi drop berkala terus-menerus dari awal, TIDAK memburuk seiring waktu). `sudo systemctl restart clearpath-platform.service` **TIDAK memperbaiki ini** (beda dgn joystick yg langsung sembuh) — indikasi kuat ini koneksi fisik BMS yang longgar/marginal, BUKAN bug software murni. Device: `/dev/clearpath/mcu` → `/dev/ttyUSB1` (dipakai bareng motor control yg jalan normal, jadi port serial-nya sendiri OK — masalahnya spesifik di parsing data battery dari stream itu). Tidak blocking navigasi. Kalau butuh battery telemetry andal, cek fisik kabel/konektor BMS.

### H) `obstacle_stop_node.py` — bug performa CPU — SUDAH FIX
Root cause: `_iter_xyz()` parse PointCloud2 PER TITIK pakai Python loop + `struct.unpack_from()` — VLP-32C punya puluhan ribu titik/scan @ 10Hz, jadi CPU 127% sustained (salah satu penyumbang terbesar overload sistem hari ini). **Fix: vectorize pakai numpy** — fungsi baru `_extract_xyz()` baca semua titik sekaligus via `np.frombuffer` + slicing per-offset, filter zone (forward/side, height) pakai boolean mask numpy, bukan Python for-loop per titik. Logic/threshold safety **SAMA PERSIS** (fwd_distance, robot_width, side_distance, dst semua gak berubah) — cuma cara parsing-nya yg beda, gak ada perubahan perilaku emergency-stop. **Hasil terverifikasi: CPU turun dari 127% → ~20% (dites langsung, Fase C jalan penuh, load sistem 12-core cuma ~12** (sehat) **vs 26 sebelumnya).** File: `semantic/obstacle_stop_node.py` (sudah di-sync ke kmp-orin via auto-rsync hook).
